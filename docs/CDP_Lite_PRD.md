# CDP Lite 产品功能需求文档（PRD）

**产品名称：** CDP Lite  
**产品定位：** 轻量级客户数据平台功能应用  
**文档版本：** V1.0  
**文档状态：** 初始需求定义  
**产品形态：** Web 管理后台

---

## 一、产品概述

### 1.1 产品背景

传统 CDP（Customer Data Platform，客户数据平台）通常包含数据采集、数据治理、元数据管理、标签加工、行为分析、人群构建、人群计算和人群分发等模块。

本项目旨在构建一个轻量级 CDP Web 应用，重点实现 CDP 的**业务功能层**，不涉及复杂的底层数据处理基础设施。系统通过配置元数据，为用户提供可视化的人群规则构建能力，形成完整的元数据管理与人群配置业务流程。

### 1.2 产品目标

1. 支持标签、属性、行为模型的创建、编辑、查询和管理。
2. 支持枚举型标签、属性和行为维度的值列表管理。
3. 支持按规则类型（标签、属性、行为模型）构建人群筛选条件。
4. 支持行为模型下的时间范围、维度筛选与指标聚合条件。
5. 支持规则组内 AND、规则组间 OR 的二维数组逻辑组合。
6. 支持人群规则保存、编辑、复制及管理。
7. 保证元数据与人群规则之间的引用关系及数据一致性。
8. 为后续接入真实 CDP 计算服务预留扩展能力。

### 1.3 产品边界

**V1.0 包含：** 元数据管理、标签管理、属性管理、行为模型管理、枚举值管理、人群管理、可视化规则编辑、规则 JSON 持久化、引用校验及基础操作反馈。

**V1.0 不包含：** 数据采集与 ETL、数据治理、数据仓库、实时计算、实际人群计算、人群规模预估、人群成员明细、人群分发、多租户、复杂权限和 AI 自动圈人。

> V1.0 创建人群的本质是保存一份结构化的规则定义，不代表已经计算出符合条件的用户集合。

## 二、系统功能架构

```text
CDP Lite
├── 元数据管理
│   ├── 标签管理
│   │   └── 标签值管理
│   ├── 属性管理
│   │   └── 属性值管理
│   └── 行为模型管理
│       ├── 维度管理
│       │   └── 维度值管理
│       └── 指标管理
└── 人群管理
    ├── 人群列表
    ├── 新建 / 编辑人群
    ├── 规则构建器
    ├── 复制人群
    └── 删除人群
```

### 2.1 元数据管理

元数据包括三类：

- **标签（Tag）**：用户的业务标签，如会员等级、消费偏好、活跃程度。
- **属性（Attribute）**：用户的基础属性，如年龄、性别、注册时间、所在城市。
- **行为模型（Event Model）**：用户发生的业务事件，如商品购买、页面访问、活动参与。每个行为模型拥有自己独立的维度集合与指标集合。

### 2.2 人群管理

人群由若干规则组组成，每个规则组可以混合包含标签、属性、行为模型三种规则类型。规则组内部使用 AND，规则组之间使用 OR。

## 三、标签与属性管理

### 3.1 通用元数据字段

| 字段 | 说明 |
| --- | --- |
| ID | 稳定的唯一标识 |
| 类型 | TAG / ATTRIBUTE |
| 名称 | 面向业务人员的展示名称 |
| 字段名称 | 英文技术字段名 |
| 描述 | 业务含义 |
| 数据类型 | String、Number、Boolean、Date、DateTime |
| 展示类型 | 文本框、数字输入、下拉单选、下拉多选、日期选择等 |
| 是否枚举 | 是否启用预定义值管理 |
| 状态 | 启用、停用 |
| 创建时间 | 创建记录时间 |
| 更新时间 | 最近修改时间 |

数据类型决定实际存储和比较语义；展示类型决定规则值输入组件。展示类型必须与数据类型、枚举配置相兼容。

| 数据类型 | 可用展示类型示例 |
| --- | --- |
| String | 文本输入、下拉单选、下拉多选 |
| Number | 数字输入、下拉单选、下拉多选 |
| Boolean | 布尔选择 |
| Date | 日期选择 |
| DateTime | 日期时间选择 |

### 3.2 标签管理

标签列表展示名称、字段名称、数据类型、展示类型、是否枚举、状态、更新时间。支持搜索、筛选、新建、查看、编辑、启停用和删除。

示例标签：

| 标签名称 | 字段名称 | 数据类型 | 是否枚举 |
| --- | --- | --- | --- |
| 会员等级 | member_level | String | 是 |
| 用户活跃分 | active_score | Number | 否 |

### 3.3 属性管理

属性列表与编辑功能和标签管理保持一致，使用独立的业务分类，但前端可以复用表单、列表和枚举值管理组件。

示例属性：年龄、性别、所在城市、注册时间。

### 3.4 枚举值管理

当标签或属性配置为枚举时，可管理其可选值。字段包括 ID、值名称、值编码、排序、状态。

示例：会员等级（member_level）。

| 值名称 | 值编码 |
| --- | --- |
| 普通会员 | NORMAL |
| 银卡会员 | SILVER |
| 金卡会员 | GOLD |
| 钻石会员 | DIAMOND |

规则构建时展示值名称，持久化保存值编码。支持新增、编辑、排序、停用和删除；被人群引用的枚举值不得直接物理删除或修改编码。

## 四、行为模型管理

### 4.1 行为模型定义

行为模型描述用户发生的一类事件，包含三层：

1. **行为模型基础信息**：行为名称、行为编码、描述、状态等。
2. **维度集合**：隶属于该行为模型的事件上下文属性。
3. **指标集合**：隶属于该行为模型的数值度量字段。

例如“商品购买（product_purchase）”行为模型：

- 维度：商品分类、商品品牌、支付渠道。
- 指标：购买金额、购买数量、优惠金额。

**从属关系约束：维度与指标必须归属于一个确定的行为模型，不允许作为跨行为模型的全局独立元数据供人群规则任意选择。**

### 4.2 行为模型基础字段

| 字段 | 说明 |
| --- | --- |
| ID | 唯一标识 |
| 行为名称 | 业务展示名称 |
| 行为编码 | 英文技术标识 |
| 描述 | 行为含义 |
| 状态 | 启用、停用 |
| 创建时间 / 更新时间 | 记录时间 |

### 4.3 行为维度管理

维度字段：ID、所属行为模型 ID、维度名称、维度字段名称、数据类型、展示类型、是否枚举、状态。

枚举型维度支持维度值管理，字段为 ID、所属维度 ID、值名称、值编码、排序、状态。

示例：商品分类（product_category）：DIGITAL（数码产品）、CLOTHING（服装鞋帽）、FOOD（食品饮料）。

### 4.4 行为指标管理

指标字段：ID、所属行为模型 ID、指标名称、指标字段名称、数据类型、描述、状态。V1.0 主要支持数值型指标。

| 指标名称 | 字段名称 | 数据类型 |
| --- | --- | --- |
| 购买金额 | purchase_amount | Number |
| 购买数量 | purchase_count | Number |
| 优惠金额 | discount_amount | Number |

### 4.5 行为模型编辑页面

采用基础信息、维度管理、指标管理三个分区。维度和指标都在**当前行为模型详情页**内维护；枚举型维度可进一步维护维度值。保存时检查维度、指标编码在所属行为模型内的唯一性及数据合法性。

## 六、人群规则构建器

### 6.1 规则层次与逻辑关系

规则体系采用三层结构：

1. **人群（Audience）**：包含多个规则组。
2. **规则组（Rule Group）**：包含多条规则；组内规则关系固定为 AND。
3. **规则（Rule）**：类型为 TAG、ATTRIBUTE 或 EVENT；每条规则内部的配置随类型变化。

规则组之间的关系固定为 OR。不同规则组、同一规则组内部都允许使用多种规则类型。

```text
人群
├── 规则组 A
│   ├── 属性规则：年龄 > 25
│   ├── AND 标签规则：会员等级 = 金卡
│   └── AND 行为规则：最近 30 天数码商品购买次数 >= 3
├── OR
└── 规则组 B
    ├── 属性规则：城市 = 上海
    └── AND 标签规则：活跃等级 = 高
```

V1.0 不支持任意深度嵌套、规则组内部 OR、规则组间 AND 或规则组 NOT。

### 6.2 新增规则的统一入口

**每次新增规则时，必须先选择规则类型：标签 / 属性 / 行为模型。**

| 规则类型 | 选择对象 | 后续配置 |
| --- | --- | --- |
| TAG | 具体标签 | 操作符、值 |
| ATTRIBUTE | 具体属性 | 操作符、值 |
| EVENT | 具体行为模型 | 时间范围、维度筛选、指标/次数聚合条件 |

规则编辑器根据类型切换表单。用户不需要直接编辑 JSON。

### 6.3 标签与属性规则交互

1. 选择规则类型 TAG 或 ATTRIBUTE。
2. 从该类型的可用元数据中选择具体字段。
3. 根据字段的数据类型选择操作符。
4. 根据数据类型、展示类型和操作符填写或选择值。

示例：

```json
{
  "metadataType": "TAG",
  "metadataId": "member-level-id",
  "operator": "EQ",
  "value": "GOLD"
}
```

`metadataId` 应使用真实稳定 ID；此处为示意值。

### 6.4 行为规则交互与配置顺序

**行为规则必须先选择具体行为模型并确定时间范围，才能配置其下的维度或指标规则。**

配置顺序：

1. **选择规则类型**：EVENT（行为模型）。
2. **选择行为模型**：例如“商品购买”。
3. **确定时间范围**：例如最近 30 天，或指定开始与结束时间。
4. **配置维度筛选**：只能选择当前行为模型下的维度；支持零条或多条维度条件。
5. **配置聚合指标条件**：选择事件发生次数，或选择当前行为模型下的数值型指标及聚合方式；设置比较操作符与目标值。

交互限制：

- 未选择行为模型，不展示可选维度和指标。
- 未配置合法时间范围，不允许进入有效的维度/指标配置状态。
- 维度与指标列表只从当前行为模型的定义中读取。
- 切换行为模型时，清空原维度与指标配置，时间范围可保留。
- 维度条件可以为空；为空时表示不按维度过滤该行为。
- V1.0 单条行为规则支持**一个聚合判断条件**；多个聚合判断可通过新增行为规则表达。
- 单条行为规则内的多个维度条件固定为 AND。

### 6.5 行为规则的计算语义

以“最近 30 天购买数码产品的总金额 > 1000 元”为例：

1. 选择商品购买事件。
2. 过滤最近 30 天内的事件记录。
3. 过滤商品分类为数码产品的记录。
4. 对筛选后的记录计算购买金额 SUM。
5. 判断 SUM 是否大于 1000。
6. 将最终布尔结果作为一条完整的行为规则，参与外层规则组 AND / OR。

因此，**维度过滤先于指标聚合**；行为规则整体作为外层逻辑中的单个布尔条件。

当同一规则组出现两条相同行为模型的行为规则时，默认分别求值后再做 AND，不要求两条规则命中同一条事件记录。

### 6.6 行为时间范围

V1.0 支持：

- 相对时间：最近 N 天（例如最近 7 天、30 天）。
- 绝对时间：指定开始时间与结束时间。

相对时间以未来实际执行规则时的计算基准时间为锚点；V1.0 仅保存定义，不执行计算。绝对时间保存明确的时间边界，前后端应统一时区约定。

### 6.7 行为维度条件

维度条件字段：维度 ID、操作符、值。操作符和值输入组件沿用普通元数据的类型驱动机制。

```json
{
  "dimensionId": "product-category-id",
  "operator": "EQ",
  "value": "DIGITAL"
}
```

维度条件之间固定为 AND。维度值若为枚举，必须来自该维度的值列表。

### 6.8 行为聚合条件

| 聚合类型 | 统计对象 | 是否需要指标 |
| --- | --- | --- |
| COUNT | 行为事件发生次数 | 否 |
| SUM | 指标求和 | 是 |
| AVG | 指标平均值 | 是 |
| MAX | 指标最大值 | 是 |
| MIN | 指标最小值 | 是 |

COUNT 为系统内置事件次数统计，不属于行为模型下的业务指标；其他聚合必须选择当前行为模型所属的数值型指标。

### 6.9 规则 JSON 结构

顶层继续采用二维数组：**内部数组 AND，外部数组 OR**。

```json
[
  [
    {
      "metadataType": "ATTRIBUTE",
      "metadataId": "age-id",
      "operator": "GT",
      "value": 25
    },
    {
      "metadataType": "TAG",
      "metadataId": "member-level-id",
      "operator": "EQ",
      "value": "GOLD"
    },
    {
      "metadataType": "EVENT",
      "eventId": "product-purchase-id",
      "timeRange": {
        "type": "RELATIVE",
        "unit": "DAY",
        "value": 30
      },
      "dimensionFilters": [
        {
          "dimensionId": "product-category-id",
          "operator": "EQ",
          "value": "DIGITAL"
        }
      ],
      "aggregation": {
        "type": "COUNT",
        "metricId": null
      },
      "operator": "GTE",
      "value": 3
    }
  ],
  [
    {
      "metadataType": "ATTRIBUTE",
      "metadataId": "city-id",
      "operator": "EQ",
      "value": "SHANGHAI"
    }
  ]
]
```

上述示例表示：

> （年龄大于 25 岁 AND 会员等级为金卡 AND 最近 30 天购买数码商品至少 3 次）OR（所在城市为上海）。

实际存储时，所有 `metadataId`、`eventId`、`dimensionId`、`metricId` 都应为系统中真实的稳定 ID。

### 6.10 规则类型定义

```typescript
type AudienceRules = AudienceRule[][];

type AudienceRule = TagRule | AttributeRule | EventRule;

type Operator =
  | 'EQ' | 'NE' | 'GT' | 'GTE' | 'LT' | 'LTE'
  | 'IN' | 'NOT_IN' | 'BETWEEN'
  | 'CONTAINS' | 'NOT_CONTAINS'
  | 'IS_NULL' | 'IS_NOT_NULL';

type RuleValue = string | number | boolean | null | Array<string | number>;

type TagRule = {
  metadataType: 'TAG';
  metadataId: string;
  operator: Operator;
  value: RuleValue;
};

type AttributeRule = {
  metadataType: 'ATTRIBUTE';
  metadataId: string;
  operator: Operator;
  value: RuleValue;
};

type TimeRange =
  | { type: 'RELATIVE'; unit: 'DAY'; value: number }
  | { type: 'ABSOLUTE'; start: string; end: string };

type DimensionFilter = {
  dimensionId: string;
  operator: Operator;
  value: RuleValue;
};

type EventRule = {
  metadataType: 'EVENT';
  eventId: string;
  timeRange: TimeRange;
  dimensionFilters: DimensionFilter[];
  aggregation: {
    type: 'COUNT' | 'SUM' | 'AVG' | 'MAX' | 'MIN';
    metricId: string | null;
  };
  operator: Operator;
  value: RuleValue;
};
```

说明：该类型定义用于表达持久化结构，操作符和值的合法组合还需通过业务校验约束。

### 6.11 操作符与输入组件

| 数据类型 | 允许的操作符 |
| --- | --- |
| String | EQ、NE、IN、NOT_IN、CONTAINS、NOT_CONTAINS、IS_NULL、IS_NOT_NULL |
| Number | EQ、NE、GT、GTE、LT、LTE、BETWEEN、IN、IS_NULL、IS_NOT_NULL |
| Date / DateTime | EQ、GT、GTE、LT、LTE、BETWEEN、IS_NULL、IS_NOT_NULL |
| Boolean | EQ、NE、IS_NULL、IS_NOT_NULL |

- `IS_NULL` / `IS_NOT_NULL`：不需要输入值，保存 `null`。
- `BETWEEN`：输入两个有序边界，保存为二元素数组。
- `IN` / `NOT_IN`：输入非空数组。
- 枚举字段：选择对应枚举值，保存值编码。
- 行为聚合结果：数值比较为主，操作符由聚合结果类型约束。

### 6.12 规则编辑器交互

人群编辑页上方为基础信息，下方为规则组列表。每组展示“添加规则”和“删除规则组”入口，组间显示 OR，组内规则之间显示 AND。

新增规则流程：

```text
点击“添加规则”
    ↓
选择类型：标签 / 属性 / 行为模型
    ├── 标签 → 选择标签 → 操作符 → 值
    ├── 属性 → 选择属性 → 操作符 → 值
    └── 行为模型 → 选择具体模型 → 时间范围
                                      ↓
                                维度条件（可选）
                                      ↓
                                指标 / 次数聚合条件
```

规则类型切换时清空原规则的专属配置，避免遗留不兼容字段。编辑行为规则时，只有当前行为模型及时间范围有效后才开放维度和指标配置。

### 6.13 保存校验

1. 至少存在一个规则组，每组至少有一条有效规则。
2. 每条规则必须有合法的规则类型。
3. 标签、属性规则必须引用对应类型的有效元数据。
4. 行为规则必须引用有效行为模型并包含合法时间范围。
5. 行为维度、指标必须属于所选行为模型。
6. 枚举值必须属于对应元数据或维度。
7. 操作符必须兼容数据类型与目标值。
8. `BETWEEN` 边界完整且顺序合法；`IN` / `NOT_IN` 为非空数组。
9. `COUNT` 的 `metricId` 必须为 `null`；其他聚合类型必须引用合法数值指标。
10. 行为规则必须有完整的聚合条件与目标比较值。
11. 已停用元数据不得用于新增规则；已有引用保留并显示状态提醒。
12. 前端即时校验，后端保存时再次完整校验。

## 七、页面设计

### 7.1 整体布局

标准 Web 管理后台：左侧导航、右侧工作区。

```text
CDP Lite
├── 元数据管理
│   ├── 标签管理
│   ├── 属性管理
│   └── 行为模型
└── 人群管理
    └── 人群列表
```

### 7.2 页面清单

| 页面 | 功能 |
| --- | --- |
| 标签列表 | 标签搜索、创建、编辑、启停用、删除 |
| 标签编辑 | 基础信息、枚举值管理 |
| 属性列表 | 属性搜索、创建、编辑、启停用、删除 |
| 属性编辑 | 基础信息、枚举值管理 |
| 行为模型列表 | 模型搜索与管理 |
| 行为模型编辑 | 基础信息、所属维度、所属指标、维度值管理 |
| 人群列表 | 查询、复制、编辑、删除 |
| 人群编辑 | 基础信息、混合类型规则组编辑、保存校验 |

### 7.3 人群规则编辑区域

普通规则横向展示：`[类型] [标签/属性] [操作符] [值] [删除]`。

行为规则建议使用可展开卡片，内部按顺序展示：

`[行为模型] → [时间范围] → [维度筛选] → [次数/指标聚合] → [比较操作符与目标值]`

行为规则卡片整体作为外层规则组中的一条条件，不能将内部维度筛选直接拆分为外层规则。

## 八、逻辑数据模型

### 8.1 Metadata

标签与属性共用逻辑实体：

`id, metadata_type, name, field_name, data_type, display_type, is_enum, description, status, created_at, updated_at`

`metadata_type` 取值为 `TAG` / `ATTRIBUTE`。

### 8.2 MetadataEnumValue

`id, metadata_id, label, value, sort_order, status`

### 8.3 EventModel

`id, name, event_code, description, status, created_at, updated_at`

### 8.4 EventDimension

`id, event_model_id, name, field_name, data_type, display_type, is_enum, status`

### 8.5 EventDimensionValue

`id, dimension_id, label, value, sort_order, status`

### 8.6 EventMetric

`id, event_model_id, name, field_name, data_type, description, status`

### 8.7 Audience

`id, name, audience_code, description, rules_json, schema_version, status, created_at, updated_at`

`rules_json` 保存二维数组结构；建议数据库使用 JSON 类型。

### 8.8 实体关系

```text
Metadata 1 ── N MetadataEnumValue
EventModel 1 ── N EventDimension
EventModel 1 ── N EventMetric
EventDimension 1 ── N EventDimensionValue
Audience ── rules_json ──> Metadata / EventModel / EventDimension / EventMetric
```

行为维度与指标仅通过所属行为模型引用；人群行为规则先引用行为模型，再引用其内部维度与指标。后端必须校验从属关系。

## 九、业务约束

### 9.1 唯一性

标签和属性的字段名称分别在各自命名空间内唯一；行为模型编码全局唯一；同一行为模型下维度与指标的字段名称应避免冲突。

### 9.2 引用与变更

已被人群引用的元数据、行为模型、维度、指标及枚举值不得直接物理删除或修改其稳定编码。允许修改展示名称与描述；停用后已有规则引用保留，新增规则不可再选择停用项。

### 9.3 行为规则依赖

- 行为模型决定可选维度与指标集合。
- 时间范围是行为规则的必填条件。
- 维度筛选先于聚合计算。
- 行为规则内部多个维度条件为 AND。
- 行为规则整体作为一个布尔条件参与外层 AND / OR。
- 相同行为模型的多条规则独立判断，不默认共享同一条事件记录。

### 9.4 删除与操作反馈

删除需要二次确认；所有创建、编辑、保存、删除提供明确反馈；校验错误显示在对应字段附近。

## 十、非功能需求

### 10.1 用户体验

简洁的企业级后台风格，统一表格、表单、弹窗及状态提示。规则编辑可视化，不要求业务用户理解 JSON。支持基础响应式布局。

### 10.2 可维护性

标签和属性复用通用组件；枚举值管理复用组件；操作符配置集中维护；行为规则编辑器与普通规则编辑器分离；规则校验与页面展示逻辑解耦。

### 10.3 可扩展性

预留真实数据计算、人群版本管理、规则快照、复杂规则树、人群分发及 AI 自然语言圈人的扩展空间。当前不引入复杂的计算引擎或通用 AST。

## 十一、V1.0 验收标准

### 11.1 元数据管理

- [ ] 可创建、编辑、查询、启停用标签和属性。
- [ ] 可管理枚举型标签、属性的值列表。
- [ ] 可创建和编辑行为模型。
- [ ] 可在具体行为模型下维护多个维度和指标。
- [ ] 可管理枚举型行为维度的维度值。
- [ ] 可校验编码唯一性和数据类型/展示类型兼容性。

### 11.2 人群构建

- [ ] 可创建人群并填写基础信息。
- [ ] 可添加多个规则组，组内 AND、组间 OR。
- [ ] 每个规则组可以混合添加标签、属性、行为模型规则。
- [ ] 每次添加规则时必须先选择规则类型。
- [ ] 标签和属性规则根据元数据类型动态显示操作符和值组件。
- [ ] 行为规则先选择具体行为模型，再确定时间范围。
- [ ] 只有完成行为模型与时间范围配置后，才能有效配置维度和指标。
- [ ] 维度和指标仅能选择当前行为模型下的定义。
- [ ] 行为规则支持多个 AND 维度筛选及 COUNT / SUM / AVG / MAX / MIN 聚合。
- [ ] 切换行为模型时能正确清空不兼容的维度和指标配置。
- [ ] 可以将混合类型规则保存为二维数组 JSON。
- [ ] 再次打开人群可以正确还原全部规则及行为配置。
- [ ] 支持复制人群、修改人群和删除人群。
- [ ] 后端可以识别无效引用和非法操作符/值组合。

### 11.3 系统整体

- [ ] 页面导航完整、操作反馈明确。
- [ ] 数据持久化，刷新后不丢失。
- [ ] 不依赖真实 CDP 数据计算引擎即可演示全部 V1.0 功能。
